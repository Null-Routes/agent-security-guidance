Log injection occurs when attacker-controlled text is written to a log without neutralising characters that carry meaning in the log format (CWE-117). The attacker can forge entries that look genuine, hide real events, break parsers and detection rules, or deliver content that is harmful to whatever later displays the log.

**How it arises**
- A text log is line-oriented and the value contains carriage returns or line feeds, so one input becomes several apparent records.
- Delimiters or field separators in the value shift fields in CSV, key=value or syslog-style output.
- A web log viewer renders values as HTML, enabling script execution in an administrator's browser ([[INPUT-006]]).
- Terminal escape sequences or control characters alter what an operator sees.
- Spreadsheets opening exported logs interpret leading formula characters.

**Illustration (generic, harmless)**

```
# Vulnerable: raw value concatenated into a line-based log
log.info("login failed for user " + username)
# If username contains a line break followed by text shaped like
# a success entry, the log now contains a second, forged-looking line.
```

**Prevent it**
- Prefer structured logging (JSON or key/value with a proper serializer) where the logging library escapes values, rather than building strings by hand.
- For text formats, replace or escape CR, LF, other control characters and format delimiters in untrusted values.
- Truncate very long values and validate fields to expected shapes ([[INPUT-002]]).
- Encode for the viewer: HTML-encode when logs are rendered in a browser ([[INPUT-005]]).
- Neutralise formula-leading characters when exporting logs to spreadsheets.
- Add correlation IDs and server-generated fields that clients cannot supply, so forged lines can be distinguished.

**Applies when** any externally influenced value (headers, parameters, filenames, identifiers, upstream error text) reaches a log. Values fully generated by the server are lower risk.
